# メモ帳（Notes App）

React + Vite で作った、CRUD・検索・Markdown対応のメモアプリです。

- 仕様の詳細は [`SPEC.md`](./SPEC.md)、アプリ内の「仕様書を見る」からも確認できます。
- このREADMEには、**ローカルでの動かし方**と、**なぜこの実装にしたのか**の両方を書いています。

---

## 1. ローカルで動かす手順

前回の「タスク帳」と基本の流れは同じです。すでにNode.jsを入れている場合は手順3から進めてください。

### 手順1: Node.jsが入っているか確認する

```bash
node -v
```

`v18.x.x` のようにバージョンが表示されればOKです。表示されない場合は
[https://nodejs.org/](https://nodejs.org/) からLTS版をインストールしてください。

### 手順2: フォルダに移動する

```bash
cd notes-app
```

### 手順3: パッケージをインストールする

```bash
npm install
```

このアプリは React 以外に **`marked`** というMarkdown変換用の小さなライブラリも使っています。
`npm install` を実行すると、これも一緒にインストールされます。

### 手順4: 開発サーバーを起動する

```bash
npm run dev
```

ターミナルに表示される `http://localhost:5173/` をブラウザで開いてください。

### 手順5: 止める・ビルドする

- 止める: ターミナルで `Control + C`
- 本番用にまとめる: `npm run build`（`dist` フォルダが作られます）
- ビルド結果を確認する: `npm run preview`

### データについて

メモはサーバーではなく、ブラウザの **localStorage** に保存されます。
同じブラウザ・同じパソコンなら消えずに残りますが、別のブラウザや別の端末とは共有されません。

## 2. なぜこの実装なのか（設計判断の解説）

初心者の方向けに、「なぜこう作ったのか」という判断の理由をまとめます。
正解が1つではない部分も多いので、「今回はこう考えた」という一例として読んでください。

### ① Markdownの変換に、自作ではなく `marked` ライブラリを使った理由

Markdown（`# 見出し`, `**太字**`, `- リスト` などの記法）を実際のHTML（見た目）に変換する処理は、
一見単純そうに見えますが、次のような例外パターンが山ほどあります。

- リストが2階層、3階層とネストした場合
- コードブロックの中に `#` や `*` のような記号がそのまま含まれる場合
- 表（テーブル）記法
- リンクの中に太字が入っている場合 など

これを自分で正確に作ろうとすると、コード量も検討事項も一気に膨れ上がります。
`marked` は世界中で広く使われ、これらのパターンをすでに考慮済みのライブラリです。
**「よくある処理は、信頼できるライブラリに任せて、自分のアプリ固有の部分に集中する」**
という判断をしています。これは実務でもよくある考え方です。

一方で、`dangerously SetInnerHTML`（変換したHTMLをそのまま画面に描画する仕組み）を使う都合上、
本来は「表示するHTMLに悪意のあるコードが混ざっていないか無害化する」処理
（`DOMPurify` などのライブラリが有名です）を組み合わせるのが安全です。
今回は「自分のブラウザに保存した、自分で書いたメモしか表示しない」個人利用のアプリなのでリスクは低いですが、
もし複数人が使うアプリや、他人が書いた文章を表示するアプリに発展させる場合は、
**必ず無害化の処理を追加してください**。この判断はコード内のコメントにも明記しています。

### ② メモのIDに `crypto.randomUUID()` を使った理由

前回の「タスク帳」では `Date.now()`（現在時刻のミリ秒）をIDとして使っていました。
シンプルで分かりやすい一方、理論上は「同じミリ秒に2つのデータが作られるとIDが重複する」
という弱点があります。タスク帳では手で1件ずつ追加するアプリだったので実害はほぼありませんが、
メモアプリでは今後「インポート機能」などで複数件を一度に作る可能性も考えられるため、
より安全な `crypto.randomUUID()`（ブラウザ標準の、重複がほぼ起こらないID生成機能）に変更しました。

このように、**同じ課題でも要件によって適切な実装が変わる**ことを、
あえて前回と違う方法を選ぶことで示しています。

### ③ 検索を「単純な文字列一致」で実装した理由

検索には、あいまい検索（表記ゆれに強い検索）や全文検索エンジンを使う方法もありますが、
今回は `includes()` という「文字列にその文字が含まれているか」を調べるだけの、
JavaScript標準の最も基本的な方法を使っています。

理由は、メモの件数が数百件程度までの個人用アプリであれば、この方法で速度的にも実用上も十分だからです。
複雑な検索の仕組みを最初から入れると、コードの見通しが悪くなり、学習の妨げにもなります。
**「今の要件に対して、十分な複雑さで実装する」**という判断です
（件数が数万件規模になったり、あいまい検索が必要になったら、その時に見直すのが現実的です）。

### ④ 状態(state)をすべて `App.jsx` に集約した理由

`notes`（メモの配列）や `selectedId`（選択中のメモ）といった状態は、
すべて `App.jsx` の中でまとめて管理し、CRUD用の関数（作成・更新・削除）もすべてそこに置いています。
各子コンポーネント（`Sidebar`, `NoteEditor` など）は自分で状態を持たず、
propsで受け取った値を表示し、操作があれば親から渡された関数を呼ぶだけです。

この設計は「状態を持ち上げる（Lifting State Up）」というReactでよく使われる考え方です。
複数のコンポーネントが同じデータ（例えば「今選ばれているメモ」）を必要とする場合、
それぞれのコンポーネントがバラバラに状態を持つと、どちらが正しい情報か分からなくなり
バグの原因になります。**「データの本体は1箇所にだけ置く」**というルールを徹底することで、
コンポーネントが増えても状態の流れを追いやすくしています。

### ⑤ `useMemo` を検索結果の計算に使った理由

`App.jsx` の中の `filteredNotes` は `useMemo` というフックで計算しています。
これは「`notes` か `searchQuery` が変化した時だけ、絞り込み処理をやり直す」ための仕組みです。

`useMemo` を使わなくても動作は変わりませんが、たとえばタイトルの入力欄にフォーカスが当たっただけの
再描画のタイミングでも、毎回全メモに対して検索処理が走ってしまいます。
メモの件数が少ないうちは体感できる差はほぼありませんが、
**「今は不要でも、無駄な再計算が起きる場所を把握しておく」**という考え方の練習として採用しています。

### ⑥ 自動保存を「デバウンス（入力の一時停止待ち）」なしにした理由

キー入力のたびに `onUpdateNote` → `setNotes` → `useEffect` で `localStorage` に書き込む、
という一番シンプルな作りにしています。実務のアプリでは「入力が0.5秒止まったら保存する」といった
デバウンス処理を入れて書き込み回数を減らすことがよくありますが、`localStorage`への書き込みは
非常に高速で、個人利用のメモ帳程度のデータ量ではパフォーマンス上の問題になりません。

**「最適化は、実際に問題が起きてから、あるいは明確に必要だと分かってから加える」**という考え方で、
あえて最初はシンプルな実装にとどめています。デバウンスの実装は、`useEffect` と `setTimeout` を
組み合わせる良い練習問題になるので、次のステップとして自分で挑戦してみるのもおすすめです。

## 3. フォルダ構成

```
notes-app/
├── README.md            … このファイル(手順+設計判断)
├── SPEC.md              … 仕様書
├── package.json
├── vite.config.js
├── index.html
└── src/
    ├── main.jsx
    ├── App.jsx                    … 状態管理とCRUD関数の中心
    ├── App.css / index.css
    ├── utils/
    │   └── storage.js              … localStorageの読み書き
    └── components/
        ├── Sidebar.jsx              … 検索欄+新規作成+一覧
        ├── SearchBar.jsx            … 検索入力欄
        ├── NoteListItem.jsx         … 一覧の1件分
        ├── NoteEditor.jsx           … 編集/プレビュー(marked使用)
        ├── EmptyState.jsx           … 未選択時の表示
        └── SpecModal.jsx            … 仕様書のモーダル表示
```

## 4. うまくいかないときは

| 症状 | 確認すること |
|------|--------------|
| `npm: command not found` | Node.jsが入っているか確認（手順1） |
| プレビューでMarkdownが反映されない | `marked` が正しくインストールされているか、`npm install` をやり直す |
| メモが消えてしまった | ブラウザやシークレットモードを変えていないか確認（localStorageは同じブラウザ内でのみ保持されます） |
